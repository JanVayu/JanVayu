# திறன்: ஆட்டோமேஷன்

ஜான்வாயுவின் (JanVayu) திட்டமிடப்பட்ட பணிகள், கேச் (cache) கட்டமைப்பு மற்றும் மீண்டும் மீண்டும் செய்யப்படும் பராமரிப்பு ஆகியவற்றை வடிவமைக்கவும் தூண்டவும் பயன்படுத்தப்படும் முறைகள் இவை — மனித தலையீடு இல்லாமல் இயங்கும் தளத்தின் பகுதிகள்.

---

## அடிப்படை கொள்கை: வெளிப்படையாகத் தோல்வியடைதல், நேர்த்தியாகச் சீரழிதல்

ஜான்வாயுவில் உள்ள ஒவ்வொரு தானியங்கி அமைப்பும் இரண்டு பண்புகளுடன் வடிவமைக்கப்பட்டுள்ளது:

1. **Fail visibly** — ஏதேனும் பழுதடையும் போது, அது அமைதியாக 500 பிழையைக் காட்டுவதற்குப் பதிலாக, தெளிவாக லாக் (log) செய்து அர்த்தமுள்ள பதிலை அளிக்கிறது
2. **Degrade gracefully** — UI வெறிச்சோடிப் போவதற்குப் பதிலாக, பழைய அல்லது பகுதி தரவுகளுடன் தொடர்ந்து செயல்படுகிறது

இந்தக் கொள்கைதான் ஒவ்வொரு ஆட்டோமேஷன் தூண்டுதலுக்கும் ஆரம்பக் கட்டுப்பாடாக இருந்தது:

```
[task]-க்காக ஒரு [scheduled/on-demand] Netlify Function-ஐ எழுதுங்கள். 
தேவைகள்:
- ஏதேனும் வெளிப்புற அழைப்பு தோல்வியடைந்தால், பிழையை சூழலுடன் (செயல்பாட்டின் பெயர், 
  நகரம்/ஃபீட், பிழை செய்தி) லாக் செய்துவிட்டுத் தொடரவும் — முழு இயக்கத்தையும் நிறுத்த வேண்டாம்
- எப்போதும் ஒரு response body-ஐத் தரவும் (ஒருபோதும் வெறும் 500-ஐ மட்டும் காட்ட வேண்டாம்)
- தரவே இல்லை என்பதை விட பழைய தரவு சிறந்தது — கேச் ரீட் (cache read) தோல்வியடைந்தால், 
  லைவ் ஃபெட்ச் (live fetch) முயற்சிக்கவும்; லைவ் ஃபெட்ச் தோல்வியடைந்தால், இருக்கும் பழைய தரவையே தரவும்
- ஒவ்வொரு திட்டமிடப்பட்ட இயக்கத்தின் தொடக்கத்தையும் முடிவையும் டைம்ஸ்டாம்புடன் (timestamp) லாக் செய்யவும்
```

## திட்டமிடப்பட்ட செயல்பாட்டு முறைகள்

### "கேச் வார்மர்" (Cache Warmer) முறை (`scheduled-fetch.mjs`)

ஒரு அட்டவணையின்படி தரவை முன்கூட்டியே பெறும் செயல்பாடுகளுக்கு:

```
[list of feeds]-ஐப் பெற்று, முடிவுகளை Netlify Blobs-ல் சேமிக்கும் ஒரு Netlify 
Scheduled Function-ஐ எழுதுங்கள். தேவைகள்:
- அனைத்து ஃபீட்களையும் இணையாகப் பெறவும் (Promise.allSettled — Promise.all அல்ல, 
  இதனால் ஒரு தோல்வி மற்றவற்றை ரத்து செய்யாது)
- ஒவ்வொரு இயக்கத்திற்குப் பிறகும் Blobs-ல் "last-fetch-time" key-ஐ எழுதவும் 
  (ISO timestamp)
- எந்தெந்த ஃபீட்கள் வெற்றி பெற்றன/தோல்வியடைந்தன மற்றும் எத்தனை உருப்படிகள் பெறப்பட்டன 
  என்பதைக் சுருக்கமாகக் கூறும் "last-fetch-log" key-ஐ எழுதவும்
- ஒரு ஃபீட் ஃபெட்ச் தோல்வியடைந்தால், எதுவும் எழுதாமல் விடுவதற்குப் பதிலாக, 
  பிழை கொடியுடன் (error flag) முந்தைய கேச் செய்யப்பட்ட மதிப்பை மீண்டும் எழுதவும்
- இந்த ஃபீட்களை வழங்கும் on-demand செயல்பாடுகள் கேச்சின் வயதைச் சரிபார்த்து, 
  அது < 4 மணி நேரத்திற்கு முந்தையதாக இருந்தால் லைவ் அழைப்பைச் செய்யாமல் அதையே வழங்க வேண்டும்
```

நிர்வாகிக்கு "Data last updated: X minutes ago" என்பதைக் காட்ட `feed-status.js` செயல்பாடு படிக்கும் விசை (key) "last-fetch-log" ஆகும் — அமைதியாக இயங்கும் ஆட்டோமேஷனை விட, கவனிக்கக்கூடிய ஆட்டோமேஷனைக் கண்டறிந்து சரிசெய்வது மிகவும் எளிது.

**`Promise.all`-க்கு பதிலாக `Promise.allSettled` ஏன்?**
எந்தவொரு வாக்குறுதியும் (promise) நிராகரிக்கப்படும் தருணத்தில் `Promise.all` அனைத்து நிலுவையில் உள்ள வாக்குறுதிகளையும் ரத்து செய்கிறது. 5+ ஆதாரங்களைக் கொண்ட ஒரு ஃபீட் வார்மரில், ஒரு ரெடிட் (Reddit) டைம்அவுட் செய்தி ஃபீட் கேச் செய்யப்படுவதைத் தடுக்கக்கூடாது. `Promise.allSettled` எல்லாவற்றையும் முடிவடையும் வரை இயக்கி, வெற்றி அல்லது தோல்வி என ஒவ்வொன்றுக்கும் ஒரு முடிவைத் தருகிறது.

### "தினசரி சுருக்கம்" (Daily Digest) முறை (`daily-digest.mjs`)

திட்டமிடப்பட்ட அட்டவணையின்படி தனிப்பயனாக்கப்பட்ட தகவல்களை அனுப்பும் செயல்பாடுகளுக்கு:

```
ஒரு Netlify Scheduled Function-ஐ எழுதுங்கள், அது:
1. Blobs-ல் இருந்து சந்தாதாரர்களின் பட்டியலைப் படிக்க வேண்டும் (மின்னஞ்சல், நகர விருப்பங்கள், வரம்பு)
2. ஒவ்வொரு சந்தாதாரருக்கும், அவர்களின் நகரத்தின் தற்போதைய AQI-ஐப் பெற வேண்டும்
3. AQI சந்தாதாரரின் வரம்பைத் தாண்டினால், Resend மூலம் மின்னஞ்சல் அனுப்ப வேண்டும்
4. பதிவு செய்ய வேண்டும்: மொத்த சந்தாதாரர்கள், அனுப்பப்பட்ட மின்னஞ்சல்கள், தவிர்க்கப்பட்ட மின்னஞ்சல்கள் (வரம்பு எட்டப்படாததால்), 
   மின்னஞ்சல் அனுப்பத் தவறியவை
5. செயல்பாடு முடிந்த பிறகு "last-email-log" என Blobs-ல் பதிவை எழுத வேண்டும்
6. எந்தவொரு சந்தாதாரரின் தோல்வியும் சுழற்சியை (loop) நிறுத்தாமல் பார்த்துக்கொள்ள வேண்டும் — ஒவ்வொரு சந்தாதாரருக்கும் ஏற்படும் பிழைகளைப் பிடித்துவிட்டு தொடர்ந்து செல்ல வேண்டும்
```

"எந்தவொரு சந்தாதாரரின் தோல்வியும் சுழற்சியை நிறுத்தாமல் பார்த்துக்கொள்ள வேண்டும்" என்பது சுருக்கத்தை (digest) அனுப்புபவருக்கு மிக முக்கியமான கட்டுப்பாடாகும். ஒரு தவறான மின்னஞ்சல் முகவரி காரணமாக மற்ற 200 சந்தாதாரர்கள் தங்கள் சுருக்கத்தைப் பெறுவதைத் தடுக்கக் கூடாது.

## Feed Freshness Architecture

கேச் (cache) புதுப்பித்தலைக் சரிபார்க்கும் முறை அனைத்து ஆன்-டிமாண்ட் ஃபீட் செயல்பாடுகளிலும் பயன்படுத்தப்படுகிறது:

```javascript
// Fetch live data-வை எடுக்க வேண்டுமா என முடிவு செய்வதற்கு முன் கேச்சின் வயதைச் சரிபார்க்கவும்
const cacheAge = Date.now() - new Date(lastFetchTime).getTime();
const FOUR_HOURS = 4 * 60 * 60 * 1000;

if (cacheAge < FOUR_HOURS && cachedData) {
  return cachedData; // கேச்சில் இருந்து வழங்கவும்
}
// இல்லையெனில்: லைவ் டேட்டாவைப் பெறவும், கேச்சை புதுப்பிக்கவும், திருப்பி அனுப்பவும்
```

**ஏன் 4 மணிநேரம்?**
Reddit மற்றும் செய்தி ஃபீட்கள் சுமார் 4 மணிநேர சுழற்சியில் கணிசமாக மாறுகின்றன. அடிக்கடி புதுப்பிப்பது ரேட் லிமிட்களை (rate limits) எட்டச் செய்யும்; குறைவாக புதுப்பிப்பது தீவிர மாசு நிகழ்வுகளின் போது பிளாட்ஃபார்மை பழையதாகக் காட்டும்.

**HTTP Cache-Control ஹெடர்களை ஏன் பயன்படுத்தக் கூடாது?**
Netlify-இன் CDN HTTP பதில்களை கேச் செய்கிறது, ஆனால் ஃபீட்களில் டைனமிக் JSON உள்ளது. Blobs-ஐ அப்ளிகேஷன்-லெவல் கேச்சாகப் பயன்படுத்துவது காலாவதி (expiry) மீது வெளிப்படையான கட்டுப்பாட்டைத் தருகிறது — அப்ஸ்ட்ரீம் CDN கேச் ஹெடர் தவறாக அமைக்கப்பட்டதால் பழைய பதில் வழங்கப்படுவதற்கு எந்த ஆபத்தும் இல்லை.

## கண்காணிப்பு முறை (Monitoring Pattern)

JanVayu `feed-status.js`-ஐ ஒரு லேசான ஹெல்த் எண்ட்பாயிண்டாகப் பயன்படுத்துகிறது:

```
ஒரு Netlify Function-ஐ எழுதுங்கள், அது Blobs கீகளைப் படிக்க வேண்டும்:
- "last-fetch-time" (கடைசி திட்டமிடப்பட்ட fetch-இன் ISO டைம்ஸ்டாம்ப்)
- "last-fetch-log" (JSON: ஒவ்வொரு ஃபீட் வெற்றி/தோல்வி/எண்ணிக்கை)
- "last-email-log" (JSON: டைஜஸ்ட் அனுப்பிய புள்ளிவிவரங்கள்)

மூன்றையும் JSON பதிலை (response) ஆகத் திருப்பி அனுப்பவும். இந்தப் பக்கம் லோட் ஆகும் போது "Feeds last updated: <time> (auto-updates every 4h)" என்பதைக் காட்ட கிளையன்ட் மூலம் இந்த எண்ட்பாயிண்ட் அழைக்கப்படுகிறது. இதில் பழைய தரவு எச்சரிக்கை (staleness warning) எதுவும் இல்லை.
```

இது முன்முனையிலிருந்து (front end) ஆட்டோமேஷனைக் கண்காணிக்கச் செய்கிறது — ஒரு பயனர் (அல்லது பராமரிப்பாளர்) Netlify டேஷ்போர்டை அணுகாமலேயே பிளாட்ஃபார்மின் தரவுப் புதுப்பித்தலைச் சரிபார்க்க முடியும்.

## Cron Timing Pattern


---
அனைத்து அட்டவணைப்படுத்தப்பட்ட செயல்பாடுகளும் UTC cron expressions-ஐப் பயன்படுத்துகின்றன. IST offset எப்போதும் வெளிப்படையாகக் கணக்கிடப்படுகிறது, அனுமானிக்கப்படுவதில்லை:

```
IST = UTC + 5:30
8:00 AM IST = 2:30 AM UTC → cron: "30 2 * * *"
Every 4 hours = "0 */4 * * *" (UTC, அதாவது 05:30, 09:30, 13:30 ... IST)
```

**ஒரு அட்டவணைப்படுத்தப்பட்ட செயல்பாட்டைப் பயன்படுத்துவதற்கு முன்பு UTC மாற்றங்களைச் சரிபார்க்க எப்போதும் Python அல்லது நம்பகமான மாற்றி (converter) கருவியைப் பயன்படுத்தவும்.** இந்தியா DST-ஐப் பின்பற்றுவதில்லை, எனவே IST offset ஆண்டு முழுவதும் நிலையான +5:30 ஆக இருக்கும்; அரை மணிநேரத்தை மறப்பதாலேயே பெரும்பாலும் தவறுகள் ஏற்படுகின்றன.

## பிற திட்டங்களுக்கு ஏற்ப மாற்றுதல்

Rate-limited அல்லது நம்பகத்தன்மையற்ற மூன்றாம் தரப்பு API-களிலிருந்து தரவைக் காட்ட வேண்டிய, API கிடைக்கும் தன்மையைப் பொருட்படுத்தாமல் வேகமான page loads-ஐ எதிர்பார்க்கும் பயனர்களைக் கொண்ட, அல்லது நிரந்தர தரவுத்தளத்தை (database) பராமரிக்க முடியாத எந்தவொரு திட்டத்திற்கும் cache-warmer + on-demand-server முறை மீண்டும் பயன்படுத்தக்கூடியது (Netlify Blobs சேவையகமற்றது மற்றும் free-tier).

முக்கியமான கட்டமைப்பு முடிவு: **fetch மற்றும் serve ஆகியவற்றைத் தனித்தனியாகப் பிரிப்பது**. அட்டவணைப்படுத்தப்பட்ட செயல்பாடு fetch செய்கிறது; on-demand செயல்பாடு serve செய்கிறது. அவை Blobs cache மூலம் மட்டுமே தொடர்பு கொள்கின்றன. இது இரண்டையும் தனித்தனியாகச் சோதிக்கவும், தனித்தனியாகப் பிழைத்திருத்தவும் (debug) உதவுகிறது.

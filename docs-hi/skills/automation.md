# स्किल: ऑटोमेशन

ये वे पैटर्न हैं जिनका इस्तेमाल JanVayu के शेड्यूल्ड टास्क, कैश आर्किटेक्चर और बार-बार होने वाले मेंटेनेंस को डिज़ाइन और प्रॉम्प्ट करने के लिए किया जाता है — यानी प्लेटफॉर्म के वे हिस्से जो बिना किसी इंसानी दखल के चलते हैं।

---

## मूल सिद्धांत: फेल विज़िबली, डिग्रेड ग्रेसफुली

JanVayu पर हर ऑटोमेटेड सिस्टम को दो खूबियों के साथ डिज़ाइन किया गया है:

1. **Fail visibly** — जब कुछ खराब होता है, तो यह साफ तौर पर लॉग करता है और एक काम का रिस्पॉन्स देता है, न कि चुपचाप 500 एरर
2. **Degrade gracefully** — UI खाली होने के बजाय पुराने या अधूरे डेटा के साथ ही रेंडर होता है

यह सिद्धांत हर ऑटोमेशन प्रॉम्प्ट के लिए शुरुआती शर्त था:

```
[task] के लिए एक [scheduled/on-demand] Netlify Function लिखें। 
ज़रूरतें:
- अगर कोई एक्सटर्नल कॉल फेल होती है, तो कॉन्टेक्स्ट (फंक्शन का नाम, 
  शहर/फीड, एरर मैसेज) के साथ एरर को लॉग करें और आगे बढ़ें — पूरा रन 
  रोकें नहीं
- हमेशा एक रिस्पॉन्स बॉडी रिटर्न करें (कभी भी रॉ 500 नहीं)
- डेटा न होने से पुराना डेटा बेहतर है — अगर कैश रीड फेल हो जाता है, तो 
  लाइव फेच ट्राई करें; अगर लाइव फेच फेल हो जाता है, तो जो भी पुराना डेटा 
  मौजूद है उसे रिटर्न करें
- हर शेड्यूल्ड रन की शुरुआत और अंत को टाइमस्टैम्प के साथ लॉग करें
```

## शेड्यूल्ड फंक्शन पैटर्न

### "Cache Warmer" पैटर्न (`scheduled-fetch.mjs`)

उन फंक्शन्स के लिए जो एक तय शेड्यूल पर डेटा पहले से फेच करते हैं:

```
एक Netlify Scheduled Function लिखें जो [list of feeds] को फेच करे और 
रिज़ल्ट्स को Netlify Blobs में स्टोर करे। ज़रूरतें:
- सभी फीड्स को पैरेलल में फेच करें (Promise.allSettled — Promise.all नहीं, 
  ताकि एक फेल होने पर बाकी न रुकें)
- हर रन के बाद Blobs में एक "last-fetch-time" की (ISO टाइमस्टैम्प) लिखें
- एक "last-fetch-log" की लिखें जो समराइज़ करे कि कौन सी फीड्स सफल/फेल 
  हईं और कितने आइटम मिले
- अगर कोई फीड फेच फेल हो जाती है, तो कुछ भी न लिखने के बजाय एरर 
  फ्लैग के साथ पिछला कैश्ड वैल्यू वापस लिखें
- जिन on-demand फंक्शन्स से ये फीड्स सर्व होती हैं, उन्हें कैश की उम्र चेक 
  करनी चाहिए और अगर यह 4 घंटे से कम पुरानी है तो लाइव कॉल किए बिना 
  ही इसे सर्व करना चाहिए
```

"last-fetch-log" की को `feed-status.js` फंक्शन पढ़ता है ताकि एडमिन को दिखाया जा सके "Data last updated: X minutes ago" — बिना आवाज़ वाले ऑटोमेशन को डीबग करने से कहीं ज़्यादा आसान, आवाज़ वाले (observable) ऑटोमेशन को डीबग करना होता है।

**`Promise.all` की जगह `Promise.allSettled` क्यों?**
जैसे ही कोई एक प्रॉमिस रिजेक्ट होता है, `Promise.all` सभी पेंडिंग प्रॉमिस को कैंसिल कर देता है। 5+ सोर्सेस वाले फीड वार्मर में, एक Reddit टाइमआउट की वजह से न्यूज़ फीड को कैश होने से नहीं रोकना चाहिए। `Promise.allSettled` हर चीज़ को पूरा होने तक चलाता है और हर एक के लिए रिज़ल्ट रिटर्न करता है, चाहे वह सफल हो या फेल।

### "Daily Digest" पैटर्न (`daily-digest.mjs`)

शेड्यूल के अनुसार पर्सनलाइज़्ड कम्युनिकेशन्स भेजने वाले फंक्शन्स के लिए:

```
एक Netlify Scheduled Function लिखें जो:
1. Blobs से सब्सक्राइबर्स की लिस्ट पढ़े (ईमेल, शहर की प्राथमिकताएं, थ्रेशोल्ड)
2. हर सब्सक्राइबर के लिए, उनके शहर का मौजूदा AQI फेच करे
3. अगर AQI सब्सक्राइबर के थ्रेशोल्ड से ज़्यादा हो, तो Resend के ज़रिए ईमेल भेजे
4. लॉग करें: कुल सब्सक्राइबर, भेजे गए ईमेल, छोड़े गए ईमेल (थ्रेशोल्ड पूरा नहीं हुआ), 
   फेल हुए ईमेल
5. रन पूरा होने के बाद लॉग को Blobs में "last-email-log" के रूप में लिखें
6. किसी एक सब्सक्राइबर की विफलता से लूप को कभी न रुकने दें — हर सब्सक्राइबर के लिए एरर्स को कैच करें और आगे बढ़ें
```

"किसी एक सब्सक्राइबर की विफलता से लूप को कभी न रुकने दें" एक डाइजेस्ट भेजने वाले के लिए सबसे ज़रूरी शर्त है। एक गलत ईमेल एड्रेस की वजह से 200 अन्य सब्सक्राइबर्स को अपना डाइजेस्ट मिलने से नहीं रुकना चाहिए।

## फीड फ्रेशनेस आर्किटेक्चर

कैश फ्रेशनेस चेक एक ऐसा पैटर्न है जिसका इस्तेमाल सभी ऑन-डिमांड फीड फंक्शन्स में किया जाता है:

```javascript
// लाइव फेच करना है या नहीं, यह तय करने से पहले कैश की उम्र चेक करें
const cacheAge = Date.now() - new Date(lastFetchTime).getTime();
const FOUR_HOURS = 4 * 60 * 60 * 1000;

if (cacheAge < FOUR_HOURS && cachedData) {
  return cachedData; // कैश से सर्व करें
}
// else: लाइव फेच करें, कैश अपडेट करें, रिटर्न करें
```

**4 घंटे ही क्यों?**
Reddit और न्यूज़ फीड्स लगभग 4-घंटे के चक्र में काफी बदलते हैं। ज़्यादा बार रिफ्रेश करने से रेट लिमिट्स हिट होती हैं; कम बार रिफ्रेश करने से सक्रिय प्रदूषण की घटनाओं के दौरान प्लेटफ़ॉर्म पुराना (stale) लगता है।

**HTTP Cache-Control हेडर का इस्तेमाल क्यों नहीं करें?**
Netlify का CDN HTTP रिस्पॉन्स को कैश करता है, लेकिन फीड्स में डायनामिक JSON होता है। एप्लिकेशन-लेवल कैश के रूप में Blobs का इस्तेमाल करने से एक्सपायरी पर स्पष्ट कंट्रोल मिलता है — अपस्ट्रीम CDN कैश हेडर के गलत सेट होने के कारण पुराना रिस्पॉन्स सर्व होने का कोई जोखिम नहीं होता।

## मॉनिटरिंग पैटर्न

JanVayu एक हल्के हेल्थ एंडपॉइंट के रूप में `feed-status.js` का इस्तेमाल करता है:

```
एक Netlify Function लिखें जो Blobs कीज़ को पढ़े:
- "last-fetch-time" (आखिरी शेड्यूल्ड फेच का ISO टाइमस्टैम्प)
- "last-fetch-log" (JSON: प्रति-फीड सफलता/विफलता/गिनती)
- "last-email-log" (JSON: डाइजेस्ट भेजने के आँकड़े)

तीनों को JSON रिस्पॉन्स के रूप में रिटर्न करें। यह एंडपॉइंट पेज लोड होने पर क्लाइंट द्वारा कॉल किया जाता है ताकि दिखाया जा सके "Feeds last updated: <time> (auto-updates every 4h)"। इसमें कोई स्टेलनेस (पुरानी जानकारी) वार्निंग नहीं है।
```

इससे फ्रंट एंड से ऑटोमेशन को मॉनिटर करना संभव हो जाता है — कोई यूज़र (या मेंटेनर) Netlify डैशबोर्ड एक्सेस किए बिना प्लेटफ़ॉर्म के डेटा की फ्रेशनेस चेक कर सकता है।

## क्रॉन टाइमिंग पैटर्न
सभी शेड्यूल्ड फ़ंक्शन्स UTC क्रॉन एक्सप्रेशन्स का उपयोग करते हैं। IST ऑफ़सेट हमेशा स्पष्ट रूप से कैलकुलेट किया जाता है, इसे मानकर नहीं चलता:

```
IST = UTC + 5:30
8:00 AM IST = 2:30 AM UTC → cron: "30 2 * * *"
हर 4 घंटे में = "0 */4 * * *" (UTC, यानी 05:30, 09:30, 13:30 ... IST)
```

**किसी शेड्यूल्ड फ़ंक्शन को डिप्लॉय करने से पहले UTC कन्वर्ज़न को वेरिफाई करने के लिए हमेशा Python या किसी भरोसेमंद कन्वर्टर का उपयोग करें।** भारत में DST नहीं माना जाता, इसलिए साल भर IST ऑफ़सेट एक समान +5:30 रहता है; गलतियाँ आमतौर पर आधे घंटे (half-hour) को भूलने की वजह से होती हैं।

## अन्य प्रोजेक्ट्स के लिए अपनाना

कैश-वार्मर + ऑन-डिमांड-सर्वर पैटर्न किसी भी ऐसे प्रोजेक्ट के लिए दोबारा इस्तेमाल किया जा सकता है जो:
- रेट-लिमिटेड या अविश्वसनीय थर्ड-पार्टी APIs से डेटा दिखाना चाहता हो
- ऐसे यूज़र्स हों जिन्हें API की उपलब्धता की परवाह किए बिना तेज़ पेज लोड की उम्मीद हो
- एक परमानेंट डेटाबेस का खर्च नहीं उठा सकता (Netlify Blobs सर्वरलेस और फ्री-टियर है)

मुख्य आर्किटेक्चरल फ़ैसला: **फ़ेच को सर्व से अलग रखें**। शेड्यूल्ड फ़ंक्शन फ़ेच करता है; ऑन-डिमांड फ़ंक्शन सर्व करता है। वे केवल Blobs कैश के ज़रिए कम्युनिकेट करते हैं। इससे दोनों को स्वतंत्र रूप से टेस्ट और डिबग किया जा सकता है।
